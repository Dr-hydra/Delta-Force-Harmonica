# 音频识别三档预设

三档由**保留的最短音符长度**区分，而不是笼统的「混音复杂度」。实测中音符长度是区分主旋律与密集伴奏最有效的判据，远强于振幅或音域。

| 预设 | 最短音符 | `minNoteFrames` | 适用 |
| --- | --- | --- | --- |
| 独奏 / 单声部 | 约 60 ms | 5 | 单乐器、单声部干净录音；伴奏一密就会跟错声部 |
| 标准 / 推荐 | 约 140 ms | 12 | 多数纯伴奏，默认档 |
| 长音优先 | 约 200 ms | 17 | 编配厚、有密集琶音；会删掉真正的十六分音符 |

`minNoteFrames` 是解码期的帧数门限（约 11.6 ms 一帧），`minDurationMs` 是解码后的第二道长度过滤，两者会叠加。把两个都往上推会删掉真旋律，所以 `minDurationMs` 保持在配对帧门限之下。

## 测量方法

`tmp-cal/`（未提交）用 Node 跑 Basic Pitch，对五个带真值旋律的合成器乐 fixture 评分。判定标准为起音落在 ±120 ms 内且音高一致（COnP 风格），指标取 F1。

| fixture | 内容 | 考察什么 |
| --- | --- | --- |
| solo | 单声部旋律，无伴奏 | 干净素材会不会误删真音符 |
| light | 旋律 + 安静贝斯 + 弱垫音 | 轻编配 |
| ensemble | 旋律 + 贝斯 + 逐拍柱式和弦 + 鼓 | 厚编配 |
| crossing | 伴奏用高两个八度的十六分琶音**穿到旋律之上** | 过松的档会不会跟着伴奏走 |
| fast | 旋律本身全是十六分音符 | 过严的档会不会删掉真旋律 |

`crossing` 和 `fast` 是一对相反的惩罚项，缺了任何一个都会得出片面结论。

## 结果

```
config              solo    light ensemble crossing     fast   mean  worst
旧 solo              100%     100%     100%       0%      97%  79%  0%
旧 balanced           93%     100%     100%       2%      93%  77%  2%
旧 ensemble           85%     100%     100%      77%      85%  89%  77%
新 solo              100%     100%     100%       0%      97%  79%  0%
新 balanced          100%     100%     100%      44%      90%  87%  44%
新 ensemble          100%     100%     100%      91%       0%  78%  0%
```

`minNoteFrames` 取舍曲线（其余参数取新 balanced）：

```
nf5  (~58ms)  crossing   0%   fast 100%
nf7  (~81ms)  crossing   0%   fast 100%
nf10 (~116ms) crossing  18%   fast 100%
nf12 (~139ms) crossing  44%   fast  90%   ← 均值与最差项最优
nf14 (~162ms) crossing  78%   fast  19%
nf17 (~197ms) crossing  91%   fast   0%
nf20 (~232ms) crossing  91%   fast   0%   （light 也开始掉到 87%）
```

## 为什么换掉旧值

旧 `balanced`（默认档）是被支配的：干净素材上丢 7% 真音符，难例上又只有 2%，两头都不占。新值在五个 fixture 里四个持平或更好，最差项从 2% 提到 44%。

旧 `ensemble` 的聚合指标（均值 89% / 最差 77%）其实比新 `balanced` 更好，仍然换掉是因为它的稳健性来自 `amplitudeQuantile: 0.26`——删掉振幅最低的 26% 音符，不管它们是不是真的。所以它在干净素材上必然丢 15%（85%），而干净纯伴奏正是当前的主要输入。相对阈值在「全是真音符」的输入上没有安全下限，这是机制问题而不是取值问题。

## 两个已知局限

**合成 fixture 不等于真实音乐。** 这套测量能证明参数之间的相对优劣和失效机制，不能证明在真实录音上的绝对表现。真实伴奏的混响、非谐波打击乐和演奏细节都没有建模。

**不要照着某个 fixture 调到极值。** `nf17` 在 `crossing` 上拿 91%，代价是 `fast` 归零——它只在「素材确实以长音为主」时才是对的选择，这也是它被命名为「长音优先」而不是「最强」的原因。

## 复现时的两个坑

1. **`outputToNotesPoly` 会原地修改传入的 `frames` / `onsets`**：它内部调用的 `constrainFrequency` 按音域把 bin 清零。缓存模型输出反复评估不同配置时，必须每次深拷贝，否则前一个配置的音域限制会残留，后评估的配置凭空变好。应用里每次解析都是新数组，不受影响。
2. **fixture 里的鼓声用固定种子噪声**。用 `Math.random()` 会让同一配置在不同运行间出现几十个百分点的差异。
